## GL-001 受控的自动学习

- 日期：2026-08-24
- 状态：已验证方法
- 来源类型：用户明确指定的通用工作方式
- 方法陈述：每次重要教学、业务结果验证或项目复盘都自动更新 Skill 包；项目专有知识保留在项目内，全局只写入脱敏、抽象的方法。
- 证据：用户明确选择“每次自动升级”，并确认单项目经验不能未经标记成为跨客户强制规则。
- 适用范围：产品数字化顾问参与的长期业务讨论、产品项目和复盘。
- 边界与反例：普通闲聊、纯格式修改、没有业务含义的代码维护不触发更新；无真实结果时不能声称经验已被验证。
- 置信度：高
- 生效影响：自动执行学习回合，并向用户报告写入位置和生效状态。

## GL-002 连锁数字化先定义经营权责与主数据

- 日期：2026-08-24
- 状态：已验证方法
- 来源类型：行业标准、主管部门文件和跨业态公开研究
- 方法陈述：设计连锁数字化产品时，应先明确总部、区域、门店、加盟商和供应商的权责，再确认门店、商品/服务、员工、会员、供应商、加盟商及指标的主数据与权威源，之后才设计跨系统流程和自动化。
- 证据：中国连锁经营协会的便利店、生活服务和数字化特许经营研究均把总部、加盟、门店、供应链、组织和数据体系视为相互依赖的能力；商务部方案要求进销存、物流、追溯和上下游数据贯通；GS1 标准把唯一标识、主数据、交易数据和事件数据作为互操作基础。
- 适用范围：零售、餐饮、生活服务及直营/加盟混合连锁。
- 边界与反例：单店或极小规模试点可以采用轻量主数据，但仍要明确唯一标识和事实来源；不能因此预建超出业务规模的平台。
- 置信度：高
- 生效影响：连锁需求访谈默认先检查组织权责、标准化/配置边界和主数据。

## GL-003 AI 场景必须同时证明价值、可评测和可治理

- 日期：2026-08-24
- 状态：已验证方法
- 来源类型：行业研究、国际标准、监管规则和学术实证
- 方法陈述：企业 AI 产品不能以“接入模型”作为完成标准；每个场景必须具备可比较的非 AI 基线、任务与数据边界、离线和线上评测、人机权责、工具权限、运行成本、失败降级及持续监控。
- 证据：CCFA/德勤零售研究指出企业级 AI 受场景、可信度、人才、工程成本和组织协同约束；NIST AI RMF 要求治理、映射、测量和管理全生命周期风险；ISO/IEC 42001 要求持续改进的 AI 管理体系；公开零售现场实验表明价值随具体工作流和既有基线显著变化。
- 适用范围：预测、推荐、计算机视觉、生成式 AI、RAG 和智能体等企业场景。
- 边界与反例：低风险、可完全撤销的内部辅助功能可采用较轻评测，但仍需明确用户告知、反馈和关闭路径；影响个人权益的决定不能只由 AI 完成。
- 置信度：高
- 生效影响：AI PRD 默认增加基线、评测集、人机协同、权限、成本、版本、降级和审计要求。

## GL-004 平台经营后台与开放 API 不等价时采用证据优先接入

- 日期：2026-08-25
- 状态：待验证经验
- 来源类型：单项目需求探索与官方接口核验
- 方法陈述：当第三方平台经营后台可展示完整指标、但公开 API 只覆盖特定挂载、应用或授权范围时，应先用官方导出或截图/OCR 建立可追溯的数据闭环，同时把 API 接入设计为能力探测后的可选通道，不把后台可见误写成接口必然可取。
- 证据：一次品牌直播数据项目中，运营后台可见单场诊断指标，而公开接口仅覆盖小程序自挂载/达人挂载直播，且存在授权、时间范围和数据延迟限制。
- 适用范围：内容平台、广告平台、电商平台及其他“后台能力大于公开接口能力”的经营数据接入。
- 边界与反例：若平台已经为目标主体开放稳定的全量官方接口或标准导出，应优先使用官方结构化数据；截图仅作为过渡、补充或审计证据。
- 置信度：中
- 生效影响：后续同类项目默认先核对数据主体、授权关系和接口范围，再承诺自动同步，并保留证据型导入方案。

## GL-005 线索主数据采用来源快照与核实值双层模型

- 日期：2026-08-25
- 状态：待验证经验
- 来源类型：单项目历史数据导入与长期线索积累方案
- 方法陈述：当线索来源字段口径不稳定、但原始证据具有追溯价值时，主数据应把不可覆盖的来源快照与后续人工核实的结构化值分层保存；自动合并只使用可解释的确定性键，模糊匹配只提供人工复核提示。
- 证据：一次连锁门店选址历史导入中，来源包含自由文本面积、租金、联系方式和旧判断；直接结构化会污染投资统计，而保留来源记录 ID、原文和核实状态可同时支持幂等导入、隐私控制和后续核实。
- 适用范围：选址线索、供应商线索、招商机会及其他多来源、弱结构化的企业主数据积累。
- 边界与反例：来源已有统一强校验结构、权威主数据 ID 和可靠同步协议时，可直接进入结构化主数据；高重复率场景可能需要独立线索池和人工合并队列。
- 置信度：中
- 生效影响：后续同类需求探索将询问来源证据保留、幂等键、核实状态、自动合并边界和统计隔离，但不会把该方案直接视为跨项目默认结论。

## GL-006 移动证据采集应将“录入”收敛为“确认上下文”

- 日期：2026-08-25
- 状态：待验证经验
- 来源类型：单项目移动数据采集方案
- 方法陈述：一线员工通过手机上传平台结果截图时，应优先从当前业务对象入口直接绑定，或由证据提取时间/标题等上下文生成候选，让员工只做一次确认；数值解析和冲突裁决留给服务端与管理员。
- 证据：一次直播数据项目中，业务明确要求员工不重复填场次与指标，多图应作为同一批次的证据，正式数据仍由管理员终审。
- 适用范围：门店巡检、直播复盘、广告投放结果、物流回单等“业务对象已存在+手机上传证据”的任务。
- 边界与反例：若证据无法稳定提供时间或身份上下文，不得静默绑定；高风险或不可逆业务仍需更强的双人复核和证据完整性校验。
- 置信度：中
- 生效影响：后续同类移动采集 PRD 会默认评估业务对象入口、自动候选、只读上下文确认、原始证据与终审分权，但在没有结果数据前不声称可降低多少操作成本。

## GL-007 门店区域主数据应分离法定区划、运营片区与商圈

- 日期：2026-08-25
- 状态：待验证经验
- 来源类型：单项目门店选址主数据治理方案
- 方法陈述：连锁门店选址系统不应把法定行政区、开发区/运营片区和消费商圈压成同一个“区域”字段；三者应分别保存权威来源、版本和重叠关系，地图或半径命中只形成待人工确认的建议。
- 证据：一次双城市门店线索治理中，法定区县、跨区功能区和规划商圈存在重叠且来源不同；分层后才能分别支持行政统计、拓展责任和商业比较。
- 适用范围：连锁零售、餐饮和生活服务的选址、拓展分区及区域经营分析。
- 边界与反例：仅在单一小区域开展的短期试点可暂时使用轻量字段，但仍需标注其是行政口径还是运营口径；缺乏正式边界时不能把圆形缓冲区当成法定归属。
- 置信度：中
- 生效影响：后续选址类项目默认检查区域类型、权威源、版本、重叠关系和人工确认机制；在其他项目验证前不作为强制结论。

## GL-008 跨系统人数指标应先确认身份域再汇总

- 日期：2026-08-25
- 状态：待验证经验
- 来源类型：单项目私域经营指标设计
- 方法陈述：当会员、客户或联系人来自不同业务系统且没有统一身份 ID 时，应分别展示各系统人数与增量，不直接相加或计算跨系统转化率；跨门店汇总还需明确是否去重。
- 证据：一次连锁经营模块设计中，小程序会员和企业微信客户分别由交易系统与客户联系系统统计，缺少稳定的跨系统身份映射，直接相加会重复计算同一自然人并产生虚假规模。
- 适用范围：会员系统、私域客户、客服联系人、内容平台粉丝等多渠道用户指标汇总。
- 边界与反例：当企业已建立经过授权、可审计且质量达标的统一客户 ID，并明确去重窗口、合并规则和撤销机制时，可以输出去重人数及可解释的跨系统转化。
- 置信度：中
- 生效影响：后续同类需求默认先核对身份域、唯一标识、去重范围和跨店口径；在更多项目验证前不作为强制结论。

## GL-009 企业 Pad 布局应先按操作姿态与任务闭环分型

- 日期：2026-08-25
- 状态：待验证经验
- 来源类型：用户提供的消费型配置界面与中国企业现场作业界面参考
- 方法陈述：企业 Pad 端应先识别浏览分析、配置决策、连续审核或高频现场作业姿态，再组合导航、主工作区、对象列表和固定行动区；不应把桌面后台等比缩小，也不应把手机信息架构直接放大。
- 证据：同一组大屏参考中，浏览型界面采用导航栏、多栏内容和支持面板；配置型界面把结果与提交固定在右侧；高频作业界面把批次、对象网格、数字输入和主操作稳定放在同一屏，表明布局结构取决于任务闭环和操作姿态，而非设备尺寸本身。
- 适用范围：零售、餐饮、生活服务、仓储、巡检、审核和其他企业 Pad / POS 工作台。
- 边界与反例：键鼠优先、以只读分析为主的管理者 Pad 可以更接近紧凑桌面结构；消费者内容浏览、手机和桌面后台不得自动继承现场作业分区。仅凭参考图无法证明具体布局能提高效率，仍需用实际任务时长、误触率和完成率验证。
- 置信度：中
- 生效影响：后续 Pad 需求探索默认先核对使用姿态、单次任务闭环、左右手/双手操作、主要输入设备、屏幕方向、网络与外设状态，再推荐概览网格、列表详情、支持面板或高频作业台。

## GL-010 生产事件应显式区分录单与现场执行归属

- 日期：2026-08-25
- 状态：待验证经验
- 来源类型：单项目生产台账责任归属设计
- 方法陈述：记录生产、施工、巡检等多人现场事件时，应分别保存录单审计身份、责任团队、现场负责人和实际参与人；不能仅凭当前登录账号推断执行者。主数据关系用于提交时校验，历史事实使用名称与编码快照；个人维度只展示可解释的参与关系，除非另有工时或贡献依据，不分摊产量、成本或绩效。
- 证据：一次集中生产场景中，实际执行存在多人协作、跨团队借调和专人代录；若把提交人直接当成生产人员，会同时扭曲责任追溯、团队统计和个人产出。
- 适用范围：央厨生产、工厂作业、仓内加工、工程施工、现场巡检及其他“多人执行、单人录入”的企业事件。
- 边界与反例：明确由单人独立完成且系统能可靠验证执行身份的低复杂度任务，可将录单人与执行人默认相同，但仍应允许更正；需要个人绩效或计件核算时，必须额外采集工时、工序、贡献权重或可核验产出，不能用参与名单替代。
- 置信度：中
- 生效影响：后续同类需求默认检查录单、责任团队、负责人、参与人、借调、快照和权限是否被混为一体；在获得试点结果前不作为跨项目强制结论。

## GL-011 数据采集完成不等于经营决策闭环

- 日期：2026-08-26
- 状态：待验证经验
- 来源类型：单项目正式数据展示反馈
- 方法陈述：证据上传、识别、复核和入库完成后，产品仍需把正式数据即时映射到业务对象列表、同口径历史比较、期间聚合和可追溯详情；待复核数据可以立即显示流程状态，但不得混入正式经营结论。
- 证据：一次播后经营数据项目中，首条截图数据已完成识别和正式入库，但业务方仍无法从原场次列表判断本场、上场、本周和本月的变化，说明采集链路与决策视图是两个独立验收层。
- 适用范围：直播复盘、广告投放、门店巡检、内容经营和其他“证据采集后需要周期比较”的企业数据产品。
- 边界与反例：只承担合规归档、且用户不需要比较或行动的证据系统可以止于可检索账本；指标语义或聚合规则未确认时，应先展示原始正式值和覆盖率，不得为了形成看板而伪造漏斗、转化率或跨口径总数。
- 置信度：中
- 生效影响：后续同类 PRD 将分别验收采集闭环和决策闭环，并检查待复核隔离、比较基线、聚合规则、数据截至时间和证据下钻；在更多项目结果验证前不作为强制默认方案。

## GL-012 多类型企业台账应由业务类型驱动字段组

- 日期：2026-08-26
- 状态：待验证经验
- 来源类型：单项目多类型合同台账设计
- 方法陈述：当同一企业台账包含关注点显著不同的业务类型时，应先保留一组跨类型可比较的通用字段，再由单一主类型驱动专属表单、筛选、列表列和导出字段；不应把所有类型字段堆进固定宽表，也不应过早建设自由字段设计器。AI 建议与人工确认事实必须分层，只有确认值才能进入正式统计。
- 证据：一次连锁企业合同管理设计中，租赁关注月租与押金、采购关注数量与结算、战略合作关注期限与退出；采用固定类型目录后，可让表单、列表、筛选、导出和 AI Schema 共用口径，同时避免未复核建议污染正式金额。
- 适用范围：合同、证照、供应商、项目档案及其他“通用骨架稳定、类型专属关注点不同”的企业台账。
- 边界与反例：类型高度动态、租户必须自定义 Schema 或确有跨类型自由组合分析需求时，可能需要受治理的字段配置平台；若所有类型关注字段基本一致，固定通用表格更简单。当前没有上线效率和准确率结果，不能声称类型驱动一定提高完成率。
- 置信度：中
- 生效影响：后续同类需求探索会优先询问通用字段、类型互斥性、专属决策字段、确认事实来源和导出口径；在获得独立项目或上线结果验证前不升级为默认原则。

## GL-013 企业功能交付应包含线上可见性验收

- 日期：2026-08-26
- 状态：待验证经验
- 来源类型：单项目线上验收反馈
- 方法陈述：涉及网页、数据迁移、权限和定时任务的企业功能，不能以本地代码完成或测试通过作为交付完成；至少应验证功能已进入发布版本、目标角色在线可见、真实业务数据生成预期结果、后台任务持续运行，并具备失败回滚证据。
- 证据：一次企业门店评分功能在本地实现后未进入线上发布包，导致线上静态资源、评分结果和调度任务均缺失；业务方登录后无法看到此前确认的规则与结果。
- 适用范围：企业后台、数据看板、自动评分、同步任务及其他由前端、数据库和后台调度共同构成的功能。
- 边界与反例：尚未授权发布的原型、离线分析或明确只交付源码的项目不要求线上可见，但必须把交付状态标记为未上线；单次在线检查也不能替代长期可用性监控。
- 置信度：中
- 生效影响：后续同类 PRD 和验收清单默认拆分代码、发布、角色可见性、真实数据与后台任务五个检查层；在更多独立项目验证前不升级为强制通用方法。

## GL-014 业务动作必须产生可见且可追溯的状态迁移

- 日期：2026-08-26
- 状态：待验证经验
- 来源类型：单项目业务闭环修正
- 方法陈述：当用户执行“归类、复核、确认、提交”等业务动作时，系统应立即改变可见状态、对应数量、进度和下一步操作，并在刷新与数据重同步后保持；仅修改隐藏标签或建议值而不改变工作队列，会让已保存动作在业务上等同于未完成。
- 证据：一次合同来源甄别中，人工分类已经写入数据库，但记录仍停留在待甄别、进度仍为零且行级操作不变，用户因此判断功能“不起效果”。改为独立中间状态后，建议事实与正式事实仍可隔离，同时形成可验收的任务闭环。
- 适用范围：资料甄别、内容审核、风险复核、主数据清洗、审批前置检查及其他队列型企业工作台。
- 边界与反例：自动保存草稿、偏好设置等非业务完成动作不必推进主流程；高风险动作可能需要复核或双人确认，但也必须显示“待复核”等明确中间状态，不能静默停留。
- 置信度：中
- 生效影响：后续队列型 PRD 将同时定义动作后的状态、数量口径、进度、刷新持久性、下一步操作和审计证据；在更多独立项目验证前不升级为强制方法。

## GL-015 商圈范围与可洽谈商业载体应分层治理

- 日期：2026-08-26
- 状态：待验证经验
- 来源类型：单项目商业载体主数据与外部调研方案
- 方法陈述：选址系统应把用于区域分析的商圈范围，与可以进入、考察、招商或洽谈的具体商业载体分开建模；外部地图只负责发现候选，正式档案和经营状态须由可追溯证据与授权人员确认，载体价值按店型和已知证据计算并展示缺失项。
- 证据：一次双城市商业载体治理中，商圈、购物中心、商业街区、社区商业和办公园区在空间粒度、招商主体及核实责任上不同；将地图变化先进入审核队列，可避免外部改名、缺失或重复记录直接污染正式主数据。
- 适用范围：连锁零售、餐饮和生活服务的拓店调研、载体档案与选址筛选。
- 边界与反例：只有少量固定合作载体、且权威数据由运营方直接提供的场景，可以不建设地图发现队列；缺少足够证据时不得输出精确价值排名，行政社区也不能自动等同于可招商载体。
- 置信度：中
- 生效影响：后续同类需求会默认核对商圈与载体边界、候选转正机制、证据新鲜度、重复合并责任和分店型评分覆盖率；在获得独立项目或上线结果验证前不升级为默认强制方案。

## GL-016 企业 Web 侧栏应由固定令牌与显式状态机控制

- 日期：2026-08-27
- 状态：已验证方法
- 来源类型：跨系统一致性反馈与用户明确确认的通用设计原则
- 方法陈述：带常驻左侧导航的企业 Web 工作台，应使用固定的展开/折叠尺寸、统一的交界折叠按钮和显式响应式状态机；侧栏不得因菜单标题、权限数量、页面类型或内容变化自动伸缩，自动进入紧凑窗口也不得覆盖用户在宽屏下保存的偏好。
- 证据：同一组织的多个系统采用各自实现后，出现侧栏宽度、收缩方式、按钮尺寸与位置不一致，增加了跨系统学习成本；业务方明确要求把 248px 展开、68px 折叠、交界按钮及宽屏/紧凑/移动四态固化为跨系统标准。
- 适用范围：具有稳定应用框架、常驻导航和多业务页面的企业后台、管理工作台及数据工作台。
- 边界与反例：营销网站、连续阅读文档、Mobile App 和 Pad 专用作业台不强制使用；采用该标准只统一应用外壳，不得顺带改变路由、权限过滤、导航分组和业务逻辑。
- 置信度：高
- 生效影响：后续企业 Web UI 需求会默认审计侧栏尺寸、菜单上限、折叠按钮、响应式状态、偏好持久化、独立滚动与无障碍；应用框架宽度或状态错误按阻断级问题处理。

## GL-017 连锁资产应区分组织归属、实物保管单位与单位内点位

- 日期：2026-08-28
- 状态：待验证经验
- 来源类型：单项目连锁固定资产事实系统升级
- 方法陈述：连锁企业管理固定资产时，应分别表达资产在组织上的部门归属、承担实物责任的门店/仓库/中台/总部等保管单位，以及货架、房间、工位等单位内点位；权限、盘点和跨单位交接主要围绕保管单位，组织报表围绕部门，点位只描述单位内位置。三者不得合并为一个“部门/门店”字段。
- 证据：一次固定资产升级中，同一批资产同时涉及总部、中台、仓库、14 家门店和 26 个尚未归类的办公单位。仅用部门或位置会导致责任范围、盘点清单和调拨接收人不清；分层后可在不猜测单位类型的前提下定义来源责任、目标接收和单位内存放信息。
- 适用范围：连锁零售、餐饮、生活服务、仓储、央厨及其他跨多实体场地管理固定资产的企业。
- 边界与反例：只有单一办公室、没有跨场地调拨和单位级责任人的小型组织可合并组织与保管范围；商品库存、原料和耗材仍应使用库存/仓储领域模型，不因位于同一仓库而纳入固定资产事实模型。当前尚无跨项目上线结果，不声称该分层必然提升盘点准确率。
- 置信度：中
- 生效影响：后续连锁资产需求探索默认分别核对组织责任、实物责任、单位内位置、跨单位确认与权限范围；在独立项目验证前不升级为通用强制原则。

## GL-018 缺少真实任务闭环的一级模块应优先可逆下线

- 日期：2026-08-29
- 状态：待验证经验
- 来源类型：单项目上线反馈与生产数据核对
- 方法陈述：企业系统中的一级模块若没有活跃任务、明确触发频率、责任角色和结果用途，且业务方无法感知价值，应先移除用户可见入口与冗余文案，而不是继续以功能完整性维持曝光；已有底层数据与约束应采用可逆保留，待真实流程成立后再恢复。
- 证据：一次固定资产系统上线后，独立盘点模块没有正式任务、明细或差异记录，业务方明确反馈未感受到价值；下线入口不会损失现有业务数据，但物理删除会增加未来恢复成本。
- 适用范围：企业后台中尚未形成固定运营节奏的任务、巡检、盘点、审批辅助和低频配置模块。
- 边界与反例：法规强制、风险极高或虽低频但必须随时可用的能力不能仅因使用少而下线；存在未完成任务、历史审计依赖或外部集成时，应先完成迁移、关闭和告知。
- 置信度：中
- 生效影响：后续功能收缩会先核对活跃数据、触发频率、责任人、结果用途、依赖和恢复成本，再选择隐藏入口、功能冻结或物理移除；在更多项目验证前不升级为默认强制原则。

## GL-019 产品能力公开表达应与方法库同源并由专业 UI 规范约束

- 日期：2026-08-30
- 状态：已验证方法
- 来源类型：用户明确指定的通用产品工作方式
- 方法陈述：产品经理对外表达自身或产品能力时，应从当前有效的方法、证据和边界建立可追溯的公开内容模型，并调用专业 UI 规范完成视觉表达；不能用视觉包装替代产品判断，也不能让设计模板反向改写业务事实。
- 证据：用户明确要求“产品数字化顾问”学习并调用“2026 小字号 UI 2.0”建设自身官网，同时要求官网表达能力、思想、方向和持续成长机制。
- 适用范围：产品能力官网、产品方法说明、公开能力地图及其他需要把产品知识转化为界面的场景。
- 边界与反例：普通 PRD 和纯业务诊断不强制生成官网或视觉稿；与产品能力无关的纯视觉任务仍由专业设计 Skill 处理。客户专有事实、原始数据和未授权证据不能因公开表达需要而进入全局 Skill 或官网。
- 置信度：高
- 生效影响：后续能力可视化任务默认先定义公开事实、证据状态和单一转化，再调用最新版 UI 规范；重要学习会同步本地能力档案，但外部发布仍需当前任务授权。

## GL-020 UI 问诊应自适应未知程度并以减法门禁控制随机性

- 日期：2026-08-30
- 状态：已验证方法
- 来源类型：用户在多轮跨系统 UI 改造后明确指定的通用工作方式
- 方法陈述：UI 设计应先读取可发现事实，再按未知程度自适应问诊；资料充分时直接确认 Design Read，缺少关键决策时每轮只问 1–3 个问题。设计前按平台、目标、对象规模、频率和证据要求确定模板，并检查身份、数据、操作、容器、说明和装饰六类重复。
- 证据：用户持续对 Web、Mobile、Pad、官网、字号、图标、侧栏和顶栏进行跨系统固化，并明确要求把“先问清需求、再设计优化、持续做减法、固定成熟素材”升级为 UI Skill 的默认闭环。
- 适用范围：企业后台、移动任务 App、Pad 作业台、企业官网、数据报表及信息可视化的设计、审计和前端改版。
- 边界与反例：减法不得删除对象身份、范围与时间、风险、权限、数据新鲜度、证据来源、错误恢复及法律安全信息；已有系统仍须先审计并确认范围，不能以方法升级授权修改后台或业务规则。
- 置信度：高
- 生效影响：后续产品咨询与 UI 任务默认先形成主要用户、首要任务、平台、保护内容、减法目标、模板和成功标准；审计发现统一说明可见问题、用户成本、调整动作和受保护内容。

## GL-021 法律文书自动化应同时验收判断、追溯与版面

- 日期：2026-08-30
- 状态：待验证经验
- 来源类型：单项目法律顾问 Skill 产品化与用户明确反馈
- 方法陈述：合同审查和协商修订工具的专业度不能只由法律意见是否完整判断，还应同时验收原文保真、修改可追溯、理由就地可读、跨平台标注稳定和逐页版面质量；排版属于法律交付的一部分，不是事后装饰。
- 证据：一次中国企业法律顾问 Skill 升级中，用户明确要求把优秀标注排版、商业与公司法判断、零售行业理解和可复用调用能力合并为统一交付标准；通用工具测试也显示块定位、失败关闭和渲染检查需要共同存在。
- 适用范围：合同DOCX审查、谈判标注稿、公司治理文件包及其他需要保留原文的法律文书自动化。
- 边界与反例：用户只要纯文本风险清单时无需强制生成DOCX；用户明确要求Word原生修订时可以采用其他标注机制，但仍须保证原文可恢复、理由可定位和版面经过验证。当前尚无跨项目长期使用结果。
- 置信度：中
- 生效影响：后续法律文书类产品需求默认把实体判断、变更定位、原稿保护、失败关闭、标注视觉和逐页渲染分别列入验收；在更多独立项目验证前不升级为通用强制原则。
