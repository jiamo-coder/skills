# 持续业务记忆规范

当用户希望长期协作、项目已有业务知识文件，或讨论产生了后续需求会复用的认知时使用本规范。

## 记忆边界

业务记忆的目标是让后续讨论继承可靠上下文，而不是保存全部聊天内容。

- 每份记忆必须绑定具体客户、产品或业务域。开始前确认当前边界，禁止将客户专有流程、数据或策略迁移到其他客户。
- 只记录会改变产品判断的信息：术语、目标、角色、流程、规则、数据口径、系统边界、约束、决策、证据和关键未知项。
- 不记录闲聊、重复表述、未经需要的个人信息、密码、令牌、私钥或其他凭据。
- 业务事实与实现事实分开。业务记忆描述“业务如何运作以及为什么”，代码、表结构和 API 细节由仓库、技术设计或 ADR 管理。

## 查找与存放

进入已有项目时先搜索项目约定、`AGENTS.md`、已有 PRD、`PRODUCT_MEMORY.md`、`CONTEXT.md`、决策记录及同类文档，并沿用现有结构。

用户已要求持续学习、项目根目录明确且不存在同类约定时，按实际内容惰性创建：

```text
docs/product/
├── PRODUCT_MEMORY.md
├── DECISIONS.md
└── LEARNINGS.md（有真实结果反馈时再创建）
```

- `PRODUCT_MEMORY.md` 保存当前有效的业务认知，不保存逐字聊天记录。
- `DECISIONS.md` 保存产品决策的原因与演变，采用追加式记录；决策变化时标记旧项已被取代，不删除历史。
- `LEARNINGS.md` 保存由上线、运营、验收或项目复盘证明的项目经验；没有真实结果证据时不创建空文件，也不把设想写成经验。
- 若项目已有 `CONTEXT.md`，其中只维护稳定的领域术语和定义，不把它变成需求文档或实现说明。
- 多业务域项目沿用已有上下文地图；没有明确边界前不要自行拆分大量文件。
- 未知项目根目录时，在回复末尾提供“待写入的认知增量”，不擅自选择存储位置，也不承诺跨任务已经持久化。

## PRODUCT_MEMORY.md 内容

根据实际信息维护以下部分；没有内容的章节无需提前创建：

1. **身份与边界**：客户/产品、适用业务域、负责人、信息有效范围、最后复核日期。
2. **业务目标与成功口径**：当前优先级、价值目标、明确非目标及其依据。
3. **参与者与组织边界**：角色、职责、组织层级、租户和数据权限边界。
4. **核心术语**：若已有 `CONTEXT.md`，这里只链接并补充产品语境，不重复定义。
5. **现状与目标流程**：稳定主流程、关键异常、人工兜底和上下游影响。
6. **业务规则与数据口径**：对产品判断有持续影响的不变量、状态、时限和指标口径。
7. **系统与数据环境**：权威数据源、上下游、同步责任和已知现实约束，不臆造接口细节。
8. **证据化洞察与假设**：使用稳定 ID，记录证据、置信度、适用范围、反例和最后复核时间。
9. **矛盾与开放问题**：尚未统一的说法、影响、待确认人和最迟决策点。

洞察和假设建议使用：

| ID | 类型 | 陈述 | 证据/来源 | 置信度 | 适用范围 | 状态 | 最后复核 |
|---|---|---|---|---|---|---|---|
| INS-001 | 假设/洞察/原则 | 可被证伪的明确陈述 | 访谈、数据、反馈或交付结果 | 低/中/高 | 角色、流程或业务域 | 待验证/有效/已推翻 | YYYY-MM-DD |

- `假设` 是等待证据的判断。
- `洞察` 必须有证据，且明确适用范围与反例。
- `原则` 需要跨场景重复验证或由用户明确确认，不能从一次个案自动推导。
- 被推翻内容保留简短记录并指向替代结论，避免未来重复犯错。

## DECISIONS.md 内容

每项产品决策使用稳定 ID，如 `PD-001`，包含：

- 日期、状态、决策人和适用范围
- 决策内容与要解决的问题
- 曾考虑的主要选项
- 选择理由、证据和接受的取舍
- 影响的流程、规则、PRD 或需求 ID
- 复核触发条件
- 取代或被取代的决策 ID

普通偏好和容易撤销的小选择无需形成决策记录。技术架构决策满足“难逆转、有真实取舍、没有背景会令人困惑”时才进入 ADR，而不是产品决策日志。

## 项目学习与全局方法库

本 Skill 已获得用户对“每次重要教学或项目复盘自动升级”的长期授权。自动升级不是把客户做法直接复制到全局，而是执行两层沉淀：

1. **项目层**：事实、决策、原始证据、专有流程和结果保存在项目自己的 `PRODUCT_MEMORY.md`、`DECISIONS.md` 或 `LEARNINGS.md`。
2. **全局层**：从项目层抽象出的可复用方法写入 Skill 的 `references/learning-ledger.md`。全局条目不得包含客户名称、自然人信息、简历、未公开经营数据、原始文档、商业秘密或凭据。

以下事件触发自动学习回合：

- 用户明确教授新的业务原则、术语体系或判断方法。
- 需求、上线结果、验收、运营指标或用户反馈验证或推翻了既有假设。
- 阶段里程碑或项目结束，且存在会改变后续产品判断的经验。
- 新经验与现有全局方法发生冲突。

普通闲聊、纯格式修改、没有业务含义的代码维护，以及没有结果证据的自我评价不触发全局更新。

### 全局条目状态

- `待验证经验`：来自单一项目、一次访谈或尚无结果证据；可作为提问线索，不能作为其他项目的默认结论。
- `已验证方法`：用户明确指定为通用原则，或被两个以上独立场景/可信结果支持；可影响默认诊断和建议。
- `存在冲突`：有可信反例或不同业态得出相反结论；使用时必须先识别适用条件。
- `已淘汰`：证据已推翻或被新方法取代；保留替代关系，不能继续作为当前建议。

### 自动升级步骤

1. 从本轮材料提取一条清晰、可证伪的方法陈述，不复制客户原话。
2. 区分证据、推断和用户明确决策，写明适用业态、组织规模、业务环节及已知反例。
3. 与全局账本按主题和陈述比对：重复证据补强原条目，冲突证据更新状态，新方法分配下一个 `GL-XXX` ID。
4. 单项目条目以 `待验证经验` 写入；满足升级条件时更新为 `已验证方法`，并记录升级依据和日期。
5. 用 `apply_patch` 做最小更新；不得重排整个账本，不得删除历史证据。
6. 回复用户本次学到了什么、更新了哪个项目文件/全局条目、当前状态是否会影响默认方法。

若 Skill 目录不可写、路径不明确或当前任务不授权本地文件修改，只输出“待写入的全局学习增量”，不得声称已经持久化。

## 每轮学习协议

1. **加载**：读取当前业务域相关记忆；只加载与本轮问题有关的部分，避免旧材料压过当前任务。
2. **识别**：从用户回答和可信材料中提取候选事实、决策、假设与洞察，并记录来源。
3. **对照**：与已有认知比较，找出新增、强化、弱化、冲突和失效项。
4. **澄清**：会改变范围、权限、成本、风险或 P0/P1 需求的冲突必须先确认；其他内容可标记为待验证。
5. **更新**：小范围更新当前有效认知；决策历史追加记录，不静默改写；避免同一事实散落多处。
6. **抽象**：触发全局学习时，去除客户专有信息，判断是补强、冲突、新增还是淘汰，并更新全局学习账本。
7. **反馈**：向用户报告有意义的认知变化、全局学习状态和剩余未知项，不逐条播报纯格式修改。

在版本评审、上线、重大反馈或指标变化后执行复盘：哪些假设成立、哪些被推翻、原因是什么、影响哪些需求，以及下一轮最值得验证的问题。没有真实反馈或数据时，不编造“经验教训”。

## 记忆质量检查

- 当前建议能否追溯到事实、决策或明确假设？
- 术语、角色、状态和指标口径是否与最新确认一致？
- 是否混入其他客户/产品的专有认知？
- 过期或冲突内容是否仍被当作当前事实？
- 洞察是否有证据、适用范围和可被推翻的条件？
- 全局方法是否已脱敏，且没有把单项目经验伪装成通用规律？
- 冲突、反例和已淘汰方法是否仍可追溯？
- 文档是否简洁到足以让新加入的产品经理或 Codex 快速建立正确心智模型？
